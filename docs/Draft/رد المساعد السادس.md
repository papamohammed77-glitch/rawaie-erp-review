# تقرير الاستشارة التقنية المعمقة - CTO Rawaea ERP

## الموضوع: تحليل وإصلاح فشل نظام المخزون وأذونات المخزن اليدوية

بصفتي المستشار التقني المعماري للمشروع، قمت بتحليل الأدلة المقدمة (Production Evidence) والكود المرفق. هذا التقرير يقدم تشخيصاً للجذور (Root Cause) وحلاً معمارياً جذرياً يضمن استقرار النظام ومنع تكرار هذه الفئة من الأخطاء.

---

## 1. تحليل الأسباب الجذرية (Root Cause Analysis)

**التشخيص: desynchronization (عدم التزامن) بين "عقد البيانات" (Data Contract) وبيئة التنفيذ.**

### لماذا حدث هذا؟

1. **الانجراف المخططي (Schema Drift):** تطور قاعدة البيانات في الإنتاج (Production) تم بشكل منفصل عن تطوير الدوال البرمجية (RPCs). تم إضافة دوال تعتمد على أعمدة "متخيلة" أو "مخطط لها" ولم يتم التأكد من وجودها فعلياً.

1. **غياب انضباط التهجير (Migration Discipline):** لا يوجد نظام آلي يضمن أن كل تغيير في الكود (RPC) يسبقه أو يرافقه تغيير متوافق في المخطط (Schema).

1. **توزيع منطق الأعمال (Distributed Logic):** وجود منطق التحقق من سياق الشركة (Company Context) داخل الـ RPC بشكل يدوي بدلاً من الاعتماد على RLS (Row Level Security) بشكل كامل، مما يجعل الكود عرضة للأخطاء البشرية عند كتابة كل دالة جديدة.

## 2. الحلول المعمارية المقترحة

### أ. معالجة حقل `completed_by` (القرار المعماري)

**التوصية: الخيار الثاني (إضافة العمود ****`completed_by`**** إلى جدول ****`stock_vouchers`****).**

- **لماذا؟** في أنظمة الـ ERP، يجب أن يكون المستند (Voucher) كائناً مكتفياً ذاتياً (Self-contained). إضافة الفاعل (Actor) الذي أتم العملية بجانب وقت الإتمام (`completed_at`) هو المعيار القياسي للتدقيق (Auditability).

- **التنفيذ:** إضافة العمود كـ `character varying` ليتوافق مع `created_by`.

### ب. ضمان عدم التكرار (Idempotency) في الاستلام الجزئي

**التصميم المقترح: استخدام "مفتاح عدم التكرار" (Idempotency Key).**

- **الميكانيكية:** إضافة عمود `last_request_id` لجدول تفاصيل الإذن أو استخدام جدول وسيط للطلبات المعالجة.

- **الحل الأبسط والأقوى:** إضافة عمود `request_id` (UUID) في جدول `inventory_log`. عند محاولة تنفيذ عملية استلام، يتم التحقق إذا كان هذا الـ `request_id` قد سجل حركة مخزنية لهذا الإذن مسبقاً.

### ج. التزامن والذرية (Concurrency & Atomicity)

- **الذرية:** يجب تنفيذ (تحديث المخزن + تسجيل السجل + تحديث حالة الإذن) في ترانزاكشن واحد.

- **التزامن:** يجب استخدام `FOR UPDATE` على صف الإذن في بداية الدالة لمنع أي عمليات متوازية على نفس المستند.

## 4. الحل التنفيذي (Production-Ready SQL)

### المرحلة الأولى: تصحيح المخطط (Schema Fix)

```sql
-- إضافة الأعمدة المفقودة لضمان توافق الـ RPC
ALTER TABLE public.stock_vouchers 
ADD COLUMN IF NOT EXISTS completed_by CHARACTER VARYING,
ADD COLUMN IF NOT EXISTS last_request_id UUID;

-- إضافة عمود لتتبع الطلبات في سجل المخزون لمنع التكرار
ALTER TABLE public.inventory_log 
ADD COLUMN IF NOT EXISTS request_id UUID;

-- إنشاء مؤشر فريد لمنع تكرار نفس الطلب (Idempotency)
CREATE UNIQUE INDEX IF NOT EXISTS idx_inventory_log_request_id 
ON public.inventory_log (request_id) 
WHERE request_id IS NOT NULL;
```

### المرحلة الثانية: تصحيح الـ RPC (Atomic & Safe)

```sql
CREATE OR REPLACE FUNCTION public.complete_manual_stock_voucher_atomic(
    p_company_id uuid,
    p_voucher_code text,
    p_user_email text,
    p_request_id uuid DEFAULT NULL
)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path TO 'public'
AS $function$
declare
    v_voucher stock_vouchers%rowtype;
    v_expected_status text;
begin
    -- 1. قفل الصف لمنع التزامن (Concurrency Control)
    select * into v_voucher
    from stock_vouchers
    where company_id = p_company_id and voucher_code = p_voucher_code
    for update;

    if not found then
        raise exception 'الإذن غير موجود أو لا ينتمي لهذه الشركة';
    end if;

    -- 2. التحقق من حالة الإذن بناءً على نوعه
    v_expected_status := case
        when v_voucher.type in ('Transfer','DirectReturn') then 'Received'
        when v_voucher.type in ('DirectSale','SupplierReturn') then 'Sent'
        else null
    end;

    if v_expected_status is null or v_voucher.status <> v_expected_status then
        raise exception 'حالة الإذن (%) لا تسمح بالإكمال. المتوقع: %', v_voucher.status, v_expected_status;
    end if;

    -- 3. التحديث النهائي (Audit fields included)
    update stock_vouchers
    set
        status = 'Completed',
        completed_at = now(),
        completed_by = p_user_email,
        updated_at = now()
    where id = v_voucher.id;

    return jsonb_build_object(
        'success', true,
        'voucher_code', p_voucher_code,
        'status', 'Completed'
    );
end;
$function$;
```

## 5. استراتيجية الاختبار (Test Strategy)

يجب تنفيذ الاختبارات التالية في بيئة Staging مطابقة للإنتاج:

1. **اختبار التكرار (Idempotency):** استدعاء دالة الاستلام بنفس الـ `request_id` مرتين متتاليتين (يجب أن يفشل الثاني أو لا يغير المخزن).

1. **اختبار التزامن (Race Condition):** محاولة إكمال الإذن من مستخدمين في نفس اللحظة (يجب أن ينجح واحد فقط بفضل `FOR UPDATE`).

1. **اختبار النوع (Type Validation):** محاولة إكمال إذن `Transfer` وهو في حالة `Draft` (يجب أن يفشل).

## 6. التوصية النهائية للمستشار (CTO Final Verdict)

- **الجذر الأساسي:** desynchronization بين فريق الـ DB وفريق الـ Backend.

- **الإصلاح الأولي:** تنفيذ SQL المرفق لإضافة `completed_by` وتصحيح الـ RPC.

- **الإصلاح الوقائي:** منع النشر (Deployment) لأي RPC دون وجود "اختبار عقد" (Contract Test) يتحقق من وجود الجداول والأعمدة المستخدمة.

- **لا تغير:** لا تقم بإضافة `branch_id` لجدول `inventory_log` حالياً؛ اعتمد على الربط عبر `voucher_id` أو `reference` الموجودين فعلياً لتقليل مخاطر التهجير.


# CTO Deep Technical Consultation - Rawaea ERP Inventory

## 1. Categorization of Evidence

| Category | Evidence |
| --- | --- |
| **PROVEN** | `completed_by` column is missing in `stock_vouchers`. |
| **PROVEN** | `inventory_log.branch_id` is missing in Production. |
| **PROVEN** | `app_settings` RLS is currently unrestricted (`qual = true`). |
| **PROVEN** | `stock_branches` uses `available_qty = qty - allocated_qty`. |
| **STATIC** | Cancel is only allowed from `Draft` status. |
| **UNKNOWN** | Exact structure of `inventory_log` (other than the missing `branch_id`). |
| **UNKNOWN** | The existence of a `van_stock` table or if it uses `stock_branches` with a special `branch_type`. |
| **TARGET DECISION** | Custody model for `DirectSale` (Warehouse -> Customer vs Warehouse -> VAN -> Customer). |
| **TARGET DECISION** | Whether to add `completed_by` or use an audit table. |

## 2. Root Cause Analysis (A)

**Root Cause:** **Lack of "Schema-First" Migration Discipline and Contract Desynchronization.**

1. **Schema Drift**: The production database schema evolved independently of the RPC development.

1. **Uncontrolled RPC Evolution**: RPCs were written based on an "ideal" or "future" schema rather than the actual state of production.

1. **Lack of Contract Testing**: There is no automated gate that verifies RPC signatures against the actual table definitions before deployment.

1. **Distributed Business Logic**: Business rules (like status transitions) are hardcoded in multiple places (RPCs, Edge Functions, Frontend), making changes fragile.

## 3. `completed_by` Recommendation (B)

**Recommendation: Option 2 (Add ****`completed_by`**** to ****`stock_vouchers`****) + Option 4 (Audit Log).**

- **Why**: For an ERP, traceability is paramount. Adding `completed_by` to the main voucher table provides immediate, indexed visibility for reporting and UI. It maintains symmetry with `created_by`.

- **Auditability**: High.

- **Backward Compatibility**: Safe (NULLable column).

- **Simplicity**: Highest.

## 4. Partial Receive Idempotency (C)

**Design: Request-based Idempotency Key.**

- **Mechanism**: A table `processed_requests` storing `request_id` (UUID) generated by the client.

- **Logic**: The RPC checks if the `request_id` exists. If yes, it returns the previous result without moving stock.

- **Alternative (No new table)**: Use a unique index on `inventory_log` for a specific `voucher_detail_id` + `client_request_token`.

## 5. Concurrency & Atomicity (D, E)

- **FOR UPDATE**: Must lock the `stock_vouchers` row AND the specific `stock_branches` rows involved at the *beginning* of the transaction.

- **Atomicity**: Mandatory. All 4 steps (Voucher update, Stock update, Log insertion, Status update) must be in one PL/pgSQL block.

## 6. Business Custody (G)

| Transaction | Source | Destination | Custody |
| --- | --- | --- | --- |
| Purchase | Supplier | Branch | Branch Stock |
| Transfer | Branch A | Branch B | Transit -> Branch B |
| Loading | Branch | VAN | Driver Custody |
| Van Sale | VAN | Customer | Sale |
| Direct Sale | Branch | Customer | Sale |
