استشارة تقنية معمقة – تحليل فشل المخزون والقسائم اليدوية
ROOT CAUSE ANALYSIS
السبب الجذري الأساسي
المشكلة ليست مجرد عمود مفقود. إنها فشل في إدارة العقود (Contract Management) بين طبقة RPC وطبقة المخطط (Schema).

الدليل القاطع:

complete_manual_stock_voucher_atomic تشير إلى completed_by غير الموجود في stock_vouchers. هذه ليست مشكلة VARCHAR بسيطة، بل دليل على أن تعريف RPC تطور في بيئة (Staging/Dev) دون أن ينعكس على Production.

inventory_log.branch_id موثق معمارياً لكنه غائب في Production. هذا يعني أن التوثيق المعماري انفصل عن التنفيذ.

عدم وجود آلية Idempotency على مستوى قاعدة البيانات للاستلام الجزئي أدى إلى هشاشة المنطق أمام إعادة المحاولة.

لماذا فشلت الإصلاحات السابقة؟
لأنها كانت إصلاحات نقطية (Point Fixes). إصلاح completed_by بإضافته فقط كان سيعالج العرض، لا السبب. السبب هو غياب طبقة عقد (Contract Layer) تمنع أي RPC من أن تصبح غير متوافقة مع المخطط.

المشكلة الأساسية مركبة من:

Schema Drift: المخطط يتحرك، والـ RPCs لا تتحرك معه (أو العكس).

Distributed Business Logic: منطق المخزون مبعثر في عدة RPCs، مما يزيد من احتمالية الانجراف.

Lack of Contract Testing: لا يوجد اختبار آلي يصرخ إذا حاولت RPC الوصول إلى عمود غير موجود.

A. CORRECT ARCHITECTURE FOR completed_by
التوصية: الخيار 2 – إضافة completed_by إلى stock_vouchers
التقييم:

المعيار	الخيار 1 (إزالة)	الخيار 2 (إضافة)	الخيار 3 (جدول تدقيق)	الخيار 4 (إعادة استخدام created_by)
قابلية التدقيق	❌ يفقد الأثر	✅ يحتفظ بمن أكمل	✅ ممتاز	❌ يخلط بين المُنشئ والمُكمل
سلامة قاعدة البيانات	✅ لا تغيير	✅ متوافق	✅ ممتاز	❌ غموض
التوافق مع الإصدارات السابقة	✅ لا يكسر شيئاً	✅ آمن	✅ آمن	❌ قد يكسر منطق التقارير
البساطة	✅ الأبسط	✅ بسيط	❌ معقد	❌ غير دقيق
مخاطر الترحيل	لا تذكر	إضافة عمود آمنة	إنشاء جدول جديد	لا تذكر
الصيانة المستقبلية	❌ يحتاج لتخمين	✅ واضح	❌ يحتاج لصيانة إضافية	❌ غير قابل للتوسع
التوصية: الخيار 2 (إضافة العمود) هو الأصح معمارياً. كل مستند في ERP يجب أن يحمل توقيع من أكمله. created_by يختلف عن completed_by. لا يمكن إعادة استخدام الأول للثاني.

نحتاج للتمييز بين:

استلامات جزئية شرعية: 30 ثم 20 ثم 50 (كلها عمليات منفصلة).

-- إذا لم يتم إدراج صف (أي كان هناك تعارض)، فهذا يعني أن هذه العملية تمت معالجتها بالفعل.
IF NOT FOUND THEN
    RAISE EXCEPTION 'DUPLICATE_MOVEMENT';

يستخدم آلية موجودة (movement_registry).

الخطوة 2: إصلاح RPC (متوافق مع Supabase)

sql
CREATE OR REPLACE FUNCTION public.complete_manual_stock_voucher_atomic(
    p_company_id uuid,
    p_voucher_code text,
    p_user_email text
)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path TO 'public'
AS $function$

declare
    v_voucher stock_vouchers%rowtype;
    v_expected_status text;
begin

    select *
    into v_voucher
    from stock_vouchers
    where company_id = p_company_id
      and voucher_code = p_voucher_code
    for update;

    if not found then
        raise exception 'الإذن غير موجود';
    end if;

    v_expected_status :=
        case
            when v_voucher.type in ('Transfer','DirectReturn') then 'Received'
            when v_voucher.type in ('DirectSale','SupplierReturn') then 'Sent'
            else null
        end;

    if v_expected_status is null or v_voucher.status <> v_expected_status then
        raise exception 'حالة الإذن لا تسمح بالإكمال';
    end if;

    update stock_vouchers
    set
        status = 'Completed',
        completed_at = now(),
        completed_by = p_user_email
    where id = v_voucher.id
      and company_id = p_company_id
      and status = v_expected_status;

    if not found then
        raise exception 'فشل إكمال الإذن';
    end if;

    return jsonb_build_object(
        'success', true,
        'voucher_code', p_voucher_code
    );

end;

$function$;

ROOT CAUSE: انجراف العقد (Contract Drift) بين المخطط وRPC بسبب غياب اختبارات التوافق الآلية.

PRIMARY FIX: إضافة العمود completed_by (إن لم يكن موجوداً) وتحديث RPC.

SECONDARY FIX: إدراج آلية فحص العقد (Contract Validation) في CI/CD.

DO NOT CHANGE:

لا تقم بإعادة هيكلة كاملة الآن. الإصلاح جراحي.
