# الخلاصة التنفيذية

**المشكلة ليست `completed_by`.**

`completed_by` هو **أول عرض ظاهر** لمشكلة أعمق:

> **لا توجد حتى الآن سلسلة Contract واحدة ومغلقة تربط Target Business Contract → Schema → RPC → Edge Function → Application → Test → Deployment Verification.**

الدليل واضح:

* Production `stock_vouchers` لا يحتوي `completed_by`.
* الـdeployed COMPLETE RPC تحاول كتابته.
* Migration غير منفذة في Production تحتوي أيضًا `completed_by`، بل وتحتوي `received_by` في POST، بينما `stock_vouchers` المثبتة في Production لا تحتوي `received_by` أيضًا.
* Production وMigration يختلفان في DirectSale وDirectReturn.
* Partial RECEIVE لديه Transaction/locking، لكنه لا يملك هوية حدث تثبت أن الطلب الثاني هو Retry للطلب الأول.
* الـCurrent application rules نفسها تقول إن DirectSale/DirectReturn لهما نموذج Branch→Branch، لكنها لا تفرض ملكية الـVAN للمستخدم.

إذن:

```text
Schema Drift
      +
RPC Drift
      +
Target Drift
      +
Business-Event Identity Gap
      +
Contract-Test Gap
      =
Inventory Failure Class
```

# A — ROOT CAUSE

## الحكم

**السبب الجذري الأساسي: Contract Governance Failure.**

وليس Schema Drift وحده.

هناك خمسة أسباب مترابطة:

### 1. Schema Drift

Production Schema وRPC deployed لا يتطابقان.

هذا مثبت مباشرة في `completed_by`.

### 2. RPC Evolution خارج Contract مغلق

تم إنشاء/تعديل RPCs بحيث أصبحت تعتمد على أعمدة ليست في Production Schema.

وهذا يعني أن:

```text
RPC
```

لم تعد تُعامل كـcompiled contract ضد:

```text
Production Schema
```

### 3. Target Drift

لدينا أكثر من نموذج لنفس Business Event.

مثلاً DirectSale:

```text
Production:
SEND → OUT
```

بينما Release Migration:

```text
SEND → OUT + IN
```

وهي Migration معلنة صراحة بأنها لم تُنفذ في Production.

### 4. Business Event Identity Gap

Partial RECEIVE يملك:

```text
voucher
+
item
+
quantity
```

لكنه لا يملك:

```text
operation_id / request_id / idempotency_key
```

يُمكّن قاعدة البيانات من معرفة:

> هل هذه العملية الجديدة هي استلام جديد أم إعادة إرسال لنفس العملية السابقة؟

### 5. Contract Testing Gap

لا يوجد في الأدلة ما يثبت وجود Gate آلي يمنع نشر RPC إذا كان يعتمد على column غير موجود في Production Schema.

وهذا هو السبب الذي سمح لـ:

```text
Schema
  ≠
RPC
```

بالوصول إلى مرحلة الاختبار.

# C — PARTIAL RECEIVE IDEMPOTENCY

هنا أرى نقطة مهمة جدًا في تحليل حسين ومراد:

## Locking ≠ Idempotency

الـRPC تستخدم:

```sql
SELECT ...
FOR UPDATE
```

وهذا ممتاز لـConcurrency.

لكن:

```text
FOR UPDATE
```

لا يعرف أن:

```text
Request B
```

هو نفس:

```text
Request A
```

مثال:

```text
100

Request A:
receive 30

Request B:
receive 30
```

بعد انتظار B للقفل:

```text
received_qty = 30
remaining = 70
```

B قد يكون:

* Receive جديدًا مشروعًا
* أو Retry لنفس A

والـdatabase لا تستطيع معرفة الفرق بدون Event Identity.

إذن:

> **Hussein محق في أن Idempotency غير مثبتة.**

والحل ليس Unique على:

```text
voucher_id + item_id
```

لأن ذلك سيمنع:

```text
30
20
50
```

وهي عمليات Partial Receive مشروعة.

# G — CUSTODY MODEL

هنا توجد نقطة تحتاج حسم Target قبل البرمجة.

## Purchase

```text
Supplier
   ↓
Warehouse
```

Inventory:

```text
Warehouse +
```

## Transfer

```text
Warehouse A
      ↓
Warehouse B
```

Target يجب أن يحدد هل الحركة الفيزيائية:

```text
OUT A
+
IN B
```

كعملية واحدة أم مرحلتين مرتبطتين.

## Loading

```text
MAIN
 ↓
VAN
```

هذا **ليس Sale**.

إن كان الـVAN يمثل Stock Branch فعليًا:

```text
MAIN qty ↓
VAN qty ↑
```

وإذا كان Target يعتبر النقل إلى عهدة وليس Stock location ثانية، فيجب ألا يُنشأ pseudo-stock بطريقة تناقض الحقيقة.

## Van Sale

```text
VAN
 ↓
Customer
```

المهم:

> لا يجوز أن يكون هناك `MAIN deduction` مرة أخرى إذا كانت البضاعة انتقلت مسبقًا إلى VAN.

أي:

```text
MAIN → VAN
```

ثم:

```text
VanSale
```

يجب ألا ينتج:

```text
MAIN ↓
VAN ↓
```

وإلا لدينا double deduction.

## Sales Return

يجب تحديد:

```text
Customer → VAN
```

ثم:

```text
VAN → Warehouse
```

أو هل Return يدخل مباشرة Warehouse؟

**UNKNOWN من الأدلة الحالية بالنسبة إلى Target النهائي.**

## DirectSale

أرى أن النموذج الأكثر اتساقًا مع مفهوم العهدة الذي تم إثباته في الوثائق هو:

```text
Warehouse
   ↓
VAN custody
```

وليس:

```text
Warehouse
   ↓
Customer
```

في نفس لحظة تحميل العهدة.

لكن يجب الفصل:

```text
DirectSale Voucher SEND
```

عن:

```text
actual customer Sale
```

فهما ليسا نفس Business Event.

وهذا يتفق مع فهم Manual Voucher الذي سبق تثبيته.

## DirectReturn

بالمثل:

```text
VAN custody
   ↓
Warehouse
```

لكن هل يتم تمثيل ذلك:

```text
OUT VAN
+
IN Warehouse
```

أم:

```text
IN Warehouse
```

فقط مع اعتبار الـVAN ownership relationship؟

**Target Decision Required.**

## Supplier Return

```text
Warehouse
 ↓
Supplier
```

Inventory:

```text
Warehouse ↓
```

## Adjustment

```text
Inventory
 ↕
Adjustment
```

ويجب أن يكون السبب/المرجع جزءًا من الحركة.
