# 1. أول تصحيح مهم للبرومبت

البرومبت المرفق يحتوي معلومات صحيحة، لكنه **ليس كله حالة حالية موثوقة**.

أوضح مثال:

البرومبت يطلب تقييم:

وهذا صحيح كـTarget معماري، لكن الفرع يحتوي بالفعل قرارًا تنفيذيًا باسم `TARGET-DECISION-001` يثبت أن الـatomic core أصبح مسؤولًا عن invariant validation وstock mutation، بينما ما زالت حالة Production مختلفة.

والأخطر أن هناك وثيقة `TARGET-THREE-WAY-REVIEW` تقول صراحة إن Target اختار:

```text

DirectReturn
Van OUT + Warehouse IN
```

وتعتبر ذلك **FIX**.

`TARGET DECISION REQUIRED`

إذن لدينا **تناقض داخل وثائق المشروع نفسها**.

وهذا وحده يثبت أن المشكلة ليست Function Bug.

## Root Cause #1 — Contract Governance Failure

الخطأ الجوهري هو:

```text
Architecture
     ↓
Target Design
     ↓
Migration
     ↓
Current Edge Functions
     ↓
Production RPC
     ↓
Production Schema
```

لم تكن هذه السلسلة **Contractually locked**.

```text

Migration implements B
Shared TS rules implement C
Production RPC still implements D
Tests validate E
```

والنتيجة:

**Schema ≠ RPC ≠ Migration ≠ Application Rules ≠ Target**

وهذا هو الـRoot Cause الأعلى.

# 5. المفاجأة الأكبر: Partial RECEIVE

هنا البرومبت **مصيب في جوهره**.

Current RECEIVE يسمح بالـPartial Receive:

```text
100
↓
Receive 30
↓
remaining = 70
↓
status remains Sent
```

والـEdge Function يبني العملية من:

```text
qty - received_qty
```

عندما لا يرسل العميل `receivedItems`. 

المشكلة:

```text
Request A
Receive 30
↓
Sent

Request A retry
Receive 30
↓
Sent
```

الـstatus وحده لا يستطيع التمييز بين:

```text
New legitimate Receive
```

و:

```text
Retry of previous Receive
```

وهذا مهم جدًا لأن وثيقة `TARGET-DECISION-001` تقول إن:

> lifecycle state transition remains the replay barrier

وتعتبر RECEIVE الثاني مرفوضًا بسبب الحالة.

**هذا الكلام صحيح للـFull Receive، لكنه ليس كافيًا للـPartial Receive.**

وهذه نقطة أعتبرها من أهم ما كشفه التحقيق.

# 6. الحل الصحيح للـPartial Receive

لا يمكن استخدام:

```text
voucher_id + item_id + qty
```

كـIdempotency Identity.

لأن:

```text
Receive 30
Receive 20
Receive 30
```

كلها قد تكون **ثلاث عمليات تجارية مشروعة**.

إذن يجب التمييز بين:

### Business Event

```text
Receive 30
```

و:

### Network Retry

```text
نفس العملية السابقة مرة أخرى
```

## الحل الصحيح

إضافة **Operation Identity** للطلب.

مثل:

```text
p_request_id uuid
```

يولده العميل مرة واحدة للعملية.

ثم Database تحفظ:

```text
voucher_id
operation_type
request_id
```

مع:

```text
UNIQUE(voucher_id, operation_type, request_id)
```

والـRPC تصبح:

```text
BEGIN

lock voucher

check request_id

if already processed:
    return original result

lock stock rows

validate remaining

update stock

insert inventory_log

update received_qty

update voucher status

record request_id

COMMIT
```

وبذلك:

```text
Receive 30 [Request A]
       ↓
SUCCESS

Retry Request A
       ↓
same request_id
       ↓
NO second movement
```

بينما:

```text
Receive 30 [Request B]
```

هو حدث جديد مشروع.

### هذه هي Idempotency الحقيقية.

وليست:

```text
status = Sent
```

# 7. CONCURRENCY

هنا التصميم الصحيح واضح.

يجب أن يكون ترتيب الـtransaction:

```text
BEGIN
   ↓
SELECT voucher
FOR UPDATE
   ↓
validate status/type
   ↓
SELECT affected stock rows
FOR UPDATE
   ↓
calculate remaining
   ↓
validate available stock
   ↓

   ↓
inventory_log
   ↓
received_qty
   ↓

   ↓

   ↓
COMMIT
```

وليس:

```text

...
later
update stock
```

لأن:

```text
A → receive 60
B → receive 60
```

يجب ألا ينجحا معًا عندما:

```text

```

الـrow locks تجعل الثانية ترى الحالة الجديدة بعد انتهاء الأولى.

# 8. Atomicity

نعم.

هذه العمليات يجب أن تكون **Business Transaction واحدة** عندما تكون جزءًا من نفس الحركة:

```text
stock_branches
+
inventory_log
+
received_qty
+
voucher status
+
audit
+
idempotency record
```

والسبب ليس فقط Database cleanliness.

بل لأن الفشل في المنتصف يمكن أن ينتج:

### Case A

```text
stock deducted
inventory_log failed
```

فتصبح الحقيقة المادية موجودة بلا history.

### Case B

```text
inventory_log inserted
stock update failed
```

فتصبح الحركة مسجلة ولم تحدث.

### Case C

```text
stock changed
received_qty unchanged
```

فتصبح Voucher state منفصلة عن Physical Stock.

### Case D

```text
stock changed
audit failed
```

فتفقد Traceability.

لذلك:

> **Business Movement = Atomic Database Transaction**

وهذا يتفق مع Target atomic core الموجود في الفرع.

# 17. Production-quality SQL — ماذا أنفذ أولًا؟

هنا أختلف مع صياغة البرومبت قليلًا.

**لا أنفذ SQL mutation أولًا.**

أول SQL يجب أن يكون **read-only contract verification**.

مثلاً:

```sql
SELECT
    n.nspname AS schema_name,
    p.proname,
    pg_get_function_identity_arguments(p.oid) AS arguments,
    p.prosecdef,
    pg_get_functiondef(p.oid) AS definition
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND p.proname IN (
      'create_manual_stock_voucher_atomic',
      'post_manual_stock_voucher_atomic',
      'complete_manual_stock_voucher_atomic',
      'cancel_manual_stock_voucher_atomic'
  );
```

ثم Schema contract:

```sql
SELECT
    table_name,
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN (
      'stock_vouchers',
      'stock_voucher_details',
      'stock_branches',
      'inventory_log',
      'audit_log'
  )
ORDER BY table_name, ordinal_position;
```

**لا تعديل.**

بعدها فقط نكتب Migration.

# 21. ما الذي يجب ألا يتغير؟

أرى أن هذه invariants يجب تثبيتها:

```text
stock_branches
    = current physical stock truth

inventory_log
    = movement history

allocated_qty
    ≠ physical movement

available_qty
    = qty - allocated_qty
```

والـstock movement يجب أن يحدث في:

```text
one atomic authoritative boundary
```

ولا تعود Edge Functions تكتب:

```text
stock_branches
inventory_log
```

مباشرة.

وهذا متوافق مع Target Atomic Core الموجود بالفعل.

# 23. الخلاصة الجنائية

لو أردت اختصار التحقيق كله في جملة واحدة:

> **`completed_by` هو العَرَض؛ أما الجريمة المعمارية فهي غياب Contract واحد ملزم يربط Target Business Semantics بـProduction Schema وبـRPC وبـApplication Rules وبالاختبارات قبل السماح بالانتقال للمرحلة التالية.**

ولهذا ظهر:

```text
completed_by
DirectSale
DirectReturn
Partial Receive
inventory_log.branch_id
Cancel
Van Custody
```

كل منها كـ"مشكلة منفصلة".

لكنها في الحقيقة **أعراض لنفس فشل الـContract Governance**.

والدليل الأقوى أن الفرع نفسه يحتوي الآن وثيقة Target تقول إن DirectSale/DirectReturn أصبحا OUT+IN، بينما `manual-voucher-rules.ts` ما زال يبنيهما كحركة واحدة، بينما Production evidence يثبت نموذجًا ثالثًا.

هذا هو السبب الذي يجب إغلاقه **قبل** أي إصلاح جديد.

---

## التقييم الذاتي

**هل تحققت من المستودعات المتاحة؟** نعم. الحساب المرتبط يتيح مستودعين: `rawaie-erp-review` و`erp-frontend`، وتم فحص شجرة الملفات الكاملة للمستودع الأساسي والـfrontend.

**هل قرأت كل ملف في المستودعين حرفيًا؟** لا أستطيع أن أدعي ذلك بأمان؛ حجم المستودعين كبير جدًا. ما فعلته هو فحص الشجرة الكاملة ثم مراجعة **جميع المواد المرتبطة مباشرة بالمشكلة والـreviews/evidence/implementation والـInventory/Voucher/Voucher UI والـRPCs**. لذلك لن أصف هذا بأنه قراءة byte-for-byte لكل ملف.

**هل اعتمدت على الذاكرة؟** لا في النتائج الأساسية.

**هل توجد استنتاجات؟** نعم، لكنني فصلتها صراحةً كـ**Target/Architectural Recommendation** ولم أقدمها كـProduction Fact.

**هل `completed_by` مثبت؟** نعم، mismatch مثبت.

**هل Partial RECEIVE idempotency مثبتة؟** لا؛ **غير مثبتة**، والـstatic analysis يبرر اعتبارها فجوة تحتاج validation.

**هل DirectSale/DirectReturn Target محسومان؟** توجد وثيقة Target في الفرع تحسمهما OUT+IN، لكن تقارير Hussein اللاحقة ما زالت تصنفهما Target Decision Required. لذلك **هناك تعارض وثائقي داخلي يجب أن يحسمه CTO**، ولا يجوز لي اعتباره قرارًا نهائيًا لمجرد وجود وثيقة Target.

**هل يوجد SQL يجب تنفيذه الآن؟** لا. أول خطوة صحيحة هي **read-only contract verification**، وليس migration.

**نسبة الثقة في Root Cause العام:** **95%**؛ لأن النمط مدعوم بتعارضات متعددة مستقلة في Schema/RPC/Rules/Migration/Target.

**نسبة الثقة في أي Target Business Decision لم يحسمه CTO:** **UNKNOWN / لا أعتبره قرارًا نهائيًا.**

**النتيجة:** المشكلة أصبحت مفهومة على مستوى أعلى من `completed_by`: **نحن بحاجة إلى تثبيت Business Movement Contract وContract Gate قبل أي Patch جديد، وإلا سنعيد إنتاج نفس الحلقة التي نحاول التخلص منها.**
