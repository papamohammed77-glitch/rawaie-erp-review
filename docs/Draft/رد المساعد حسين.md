### 1. المصدر المعماري

الـArchitecture Constraints يفرض:

* عدم تشخيص أي Function بمعزل عن Schema وProduction Evidence وOriginal وArchitecture.
* Production Reality + Production Evidence هي المرجع النهائي عند التعارض.
* عدم اختراع Schema أو RPC signature.
* `stock_branches` = Current Stock State.
* `inventory_log` = Inventory Movement History.
* Inventory mutations يجب أن تتجه إلى Central Atomic Inventory Engine.
* لا Code Before Target Reconciliation.

### 2. Production Schema المثبت

Evidence الحديثة تثبت وجود:

`stock_vouchers`:

* `company_id`
* `voucher_code`
* `status`
* `sent_date`
* `received_date`

و`stock_voucher_details`:

* `voucher_id`
* `item_id`
* `item_code`
* `qty`
* `received_qty`

و`stock_branches`:

* `branch_id`
* `item_id`
* `qty`
* `allocated_qty`

والتكليف نفسه يثبت أن Production `stock_vouchers` **لا يحتوي `completed_by`**، رغم أن RPC المنشورة تحاول الكتابة إليه.

### 3. Production `post_manual_stock_voucher_atomic`

الـProduction Evidence الحديثة تثبت أن الـRPC:

* `SECURITY DEFINER`
* لا تسمح بالتنفيذ العام.
* تقفل الـVoucher بـ`FOR UPDATE`.
* SEND يتطلب `Draft`.
* RECEIVE يتطلب `Sent`.
* SEND يسمح بـ:

  * `Transfer`
  * `DirectSale`
  * `SupplierReturn`
* RECEIVE يسمح بـ:

  * `Transfer`
  * `DirectReturn`
* تتحقق من `company_id` للفرع والصنف.
* تستخدم `stock_branches.qty` و`allocated_qty`.
* تستخدم `FOR UPDATE` على stock row.
* تكتب `inventory_log`.
* تحدث `received_qty` عند RECEIVE.
* تغير حالة الـVoucher بعد الحركة.

### 4. Current Edge Functions

الـCurrent Functions لا تعدل المخزون مباشرة.

هي تستدعي RPC:

* Create → `create_manual_stock_voucher_atomic`
* Send → `post_manual_stock_voucher_atomic(... SEND ...)`
* Receive → `post_manual_stock_voucher_atomic(... RECEIVE ...)`
* Complete → `complete_manual_stock_voucher_atomic`
* Cancel → `cancel_manual_stock_voucher_atomic`

### 5. Current shared business rules

الـCurrent shared rules تعرف Lifecycle Types الأربعة:

`Transfer`
`DirectSale`
`DirectReturn`
`SupplierReturn`

وتعرف:

```text
OUTBOUND_ON_SEND:
Transfer
DirectSale
SupplierReturn

INBOUND_ON_RECEIVE:
Transfer
DirectReturn
```

كما أن `DirectSale` يتطلب:

`Branch → Branch`

والـCreate Function تحول الطرف الثاني تلقائيًا إلى:

`VAN-<user.email>`

عند DirectSale، وDirectReturn يعكس الاتجاه.

### 6. Original

Original كان ينفذ Stock Mutation داخل Edge Functions نفسها:

* `send-stock-voucher` يعدل `stock_branches.qty` ويكتب `inventory_log`.
* `receive-stock-voucher` يعدل `stock_branches.qty` ويكتب `inventory_log`.
* `create-stock-voucher` ينشئ Voucher وDetails.
* `complete-stock-voucher` يعدل `status/completed_at/completed_by`.
* `cancel-stock-voucher` يعدل `status` إلى `Cancelled`.

### 7. Current مقارنةً بـ Original

الـCurrent نقل Stock Mutation إلى RPC مركزية بدل أن تنفذها Edge Functions مباشرة، مع إبقاء Edge Functions كـAPI/Authorization/Orchestration boundary. هذا متوافق مع المبدأ المعماري المسجل في المشروع.

# ROOT CAUSE

## Root Cause #1 — مثبت

هناك **Schema/RPC Contract Mismatch** في COMPLETE:

```text
Production Schema
        ↓
stock_vouchers
        ↓
NO completed_by

Production RPC
        ↓
UPDATE stock_vouchers
SET completed_by = p_user_email
```

وهذا ليس مجرد Test Harness issue؛ التكليف نفسه يسجل أن المشكلة مثبتة داخل الـRPC المنشورة.

والـCurrent Edge Function يستدعي هذه الـRPC مباشرة، وبالتالي المشكلة تقع في المسار التنفيذي الفعلي:

```text
complete-stock-voucher
        ↓
complete_manual_stock_voucher_atomic
        ↓
UPDATE completed_by
        ↓
Schema Contract لا يحتوي العمود
```

## Root Cause #2 — عدم تطابق Target/Production في DirectSale

لدينا Evidence مستقل يثبت اختلافًا حقيقيًا:

### Migration

DirectSale في `post_manual_stock_voucher_atomic` يحتوي منطقًا يسمح:

```text
OUT → from_id
IN  → to_id
```

### Production V4

النسخة المنشورة المثبتة تسمح في SEND فقط:

```text
OUT → from_id
```

ولا تقبل `IN` في SEND.

والـCurrent Edge Function يبني DirectSale كـOUT فقط.

إذن لدينا **Target/Production/Current discrepancy حقيقية** تحتاج Reconciliation قبل أي تعديل.
