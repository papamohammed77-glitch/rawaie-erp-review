النتيجة CTO

بعد فحص ما يمكن إثباته من المستودع وسجل الإصلاحات، المشكلة الحقيقية أعمق من completed_by.

الـPrompt الذي قدمته يحتوي على أساس قوي، لكنه غير صالح كـTechnical Decision Document بصورته الحالية؛ لأنه يخلط بين:

Bug مثبت
و
Root Cause محتمل
و
Target Architecture
و
Business Decision لم يُحسم بعد.

وهذا بالضبط النوع من الخلط الذي تسبب في الدوران السابق.

1. ما الذي أثبته تاريخ الإصلاحات؟

سجل PRs يوضح ثلاث مراحل متتالية لـsend-stock-voucher:

PR #1: إضافة CAS على مستوى خصم المخزون.
PR #2: نقل العملية إلى PostgreSQL transaction primitive وجعل خصم عدة أصناف + inventory_log + حالة الإذن داخل transaction.
PR #3: تشديد Company Context باستخدام .single() وSELECT ... INTO STRICT. PR #1 PR #2 PR #3

وهذا يكشف شيئًا مهمًا:

كل إصلاح عالج طبقة من المشكلة، ثم ظهرت طبقة أخرى.

CAS → Atomicity → Company Context.

إذن المشكلة ليست خطأ SQL منفردًا.

المشكلة هي غياب Contract موحد للعملية من البداية.

2. Root Cause الحقيقي

أقيّم السبب الجذري كالتالي:

P0 — غياب Contract موحد بين Schema وRPC وBusiness Operation

الذي سمح بوصول:

RPC
  ↓
references completed_by
  ↓
Production Schema
  ↓
completed_by غير موجود

ليس مجرد "خطأ مطور".

بل فشل في:

Design Contract
        ↓
Schema Contract
        ↓
RPC Contract
        ↓
Migration
        ↓
Deployment
        ↓
Contract Test

هذه السلسلة لم تكن محكومة بحارس واحد.

وهذا هو Root Cause الرئيسي.

3. الخطأ الثاني: اعتبار CAS حلاً للـConcurrency

الـOriginal استخدمت:

read stock
    ↓
CAS UPDATE

وهذا يحمي صف المخزون من الكتابة فوق قيمة قديمة.

لكن هذا لا يحل وحده:

Voucher lifecycle concurrency
+
Partial receive concurrency
+
Duplicate request
+
Multi-item atomicity

PR #2 نفسه نقل العملية إلى transaction primitive، وهو اتجاه معماري صحيح، لكنه لا يثبت أن كل حالات الـConcurrency أصبحت مغلقة؛ التقرير نفسه يصرح بأن اختبارات التكامل والـconcurrency لم تُنفذ. تقرير INV-SPRINT-001

4. الخطأ الأخطر في صياغة Partial Receive

هذه العبارة في الـPrompt:

"لا يوجد idempotency لذلك إعادة نفس الطلب قد تضيف 40 مرة أخرى."

صحيحة من حيث الخطر، لكنها ليست كافية معماريًا.

لأن:

Receive 40
Receive 40

قد يكون:

حالة A — طلب جديد مشروع

المستخدم يريد:

40 + 40

وهذا يجب أن يُسمح به.

أو:

حالة B — Retry لنفس العملية

المستخدم أرسل:

request X

حدث timeout.

ثم أُعيد:

request X

وهذا يجب ألا يكرر الحركة.

إذن:

Voucher + quantity ليسا Idempotency Identity.

هذه نقطة مهمة جدًا.

5. الحل الصحيح للـIdempotency

Target الصحيح يجب أن يميز:

Business Operation

عن:

Network Retry

لذلك نحتاج هوية للعملية نفسها، مثل:

operation_id / idempotency_key

ويكون لكل عملية استلام فعلية:

Voucher
+
Voucher Detail
+
Operation ID
+
Received Qty
+
Actor
+
Timestamp

مع قيد uniqueness مناسب.

فتصبح:

Receive #1 → operation A → 40
Receive #2 → operation B → 20
Retry      → operation A → لا حركة جديدة

وهذا أفضل بكثير من محاولة جعل:

voucher_detail_id + qty

مفتاحًا فريدًا.

6. Concurrency: أين يجب أن يكون Lock؟

في حالة:

Remaining = 100

A → Receive 60
B → Receive 60

الـTarget ليس فقط:

FOR UPDATE stock

بل يجب أولًا حماية مصدر الحقيقة للعملية المستلمة.

أي:

BEGIN

Lock voucher/detail
        ↓
Read authoritative received_qty
        ↓
Calculate remaining
        ↓
Lock stock row(s)
        ↓
Validate
        ↓
Mutate stock
        ↓
Update received_qty
        ↓
Write inventory_log
        ↓
Transition voucher state if applicable
        ↓
COMMIT

فالطلب الثاني يجب أن يرى:

remaining = 40

ثم يرفض 60.

وليس أن يعتمد على قراءة قديمة للـremaining.

7. Multi-item Atomicity

هنا الإصلاح في PR #2 يسير في الاتجاه الصحيح.

إذا كان:

Item A → خصم 50
Item B → غير متاح

فالنتيجة الصحيحة:

A = unchanged
B = unchanged
Voucher = unchanged
Logs = none

وليس:

A = -50
B = failure
Voucher = Draft

إذن هذه الآثار يجب أن تقع داخل Atomic Boundary واحدة.

الـPrompt يطرح أربع خيارات.

10. المشكلة التي أراها في send_stock_voucher_atomic

الـRPC في PR #2 يحمل اتجاهًا صحيحًا، لكن توجد نقاط يجب ألا نعتبرها مغلقة:

أولًا
p_company_id

ما زال parameter.

في Target V1 يمكن قبوله كجزء من internal contract، لكن يجب ألا يكون هو مصدر الحقيقة.

الأفضل أن تكون هناك طبقة:

Authoritative Company Context
        ↓
Validated against voucher
        ↓
Validated against branch

وليس:

client → company_id → trusted
ثانيًا

هذا:

where i.company_id = p_company_id

جيد كحاجز.

لكن لا يكفي وحده لإثبات أن:

voucher branch
belongs to company

وهذه هي نقطة Company → Branch → Stock ownership التي يجب أن تكون صريحة.

ثالثًا

هذا:

select i.id
...
order by (i.id = v_detail.item_id) desc
limit 1;

يستحق المراجعة.

لأننا لا نريد Resolution logic يسمح نظريًا بوجود:

item_id = A
item_code = B

ثم يقرر أحدهما بصمت.

Target الأفضل:

Resolve by authoritative identity and reject conflicting identity.

وليس:

اختر واحدًا بـORDER BY.

الخلاصة التنفيذية

أهم اكتشاف من هذا التحقيق:

المشكلة ليست completed_by.

وليست FOR UPDATE.

وليست CAS.

وليست حتى send-stock-voucher.

المشكلة هي أن النظام بدأ تنفيذ Inventory قبل تثبيت Contract كامل يربط:

Business Event
      ↓
Custody
      ↓
Voucher Lifecycle
      ↓
Inventory Mutation
      ↓
Inventory Log
      ↓
Audit
      ↓
Concurrency
      ↓
Idempotency
      ↓
Company Isolation
      ↓
Schema/RPC Contract

والـPR #1 → #2 → #3 يوضح ذلك عمليًا: تم حل طبقة، ثم اكتشاف طبقة أخرى. سجل PRs للمستودع

لذلك لا أريد أن نضيف Migration أخرى الآن.

القرار الصحيح من موقعي كـCTO:

نوقف سلسلة الترقيعات عند send_stock_voucher_atomic، نعتبرها Implementation Candidate وليست Target، ونثبت أولًا Inventory Domain Contract + Custody Matrix + Voucher Lifecycle + Atomic/Idempotency Contract. بعد ذلك فقط نقيس الـCurrent عليه ونكتب الإصلاح.

الملخص النهائي
تم إنجازه: تحليل الـPrompt نفسه، واستخراج Root Cause المعماري، وفحص مسار الإصلاحات الثلاثة الخاصة بـsend-stock-voucher.
ما لم يتم إنجازه: لا أدّعي أنني قرأت كل ملف في المستودع؛ ففهرس الكود غير متاح حاليًا عبر GitHub connector.
القرار: لا Patch جديد الآن.
الخطوة التالية: تثبيت Inventory Domain Contract ثم Custody Matrix ثم Voucher Lifecycle Contract.
درجة الثقة: 92% في التشخيص المعماري المستخلص من الأدلة المتاحة، وأقل من ذلك في أي ادعاء يتعلق بملفات لم أتمكن من قراءتها مباشرة.
حالة الالتزام: لا يوجد تخمين مقنع على أنه حقيقة، ولا أوصي بتغيير Schema أو RPC قبل إثبات الـContract.
